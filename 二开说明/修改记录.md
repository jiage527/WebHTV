## 四、几个值得记录的「实测结论」

这些是开发过程中用真机或代码实测推翻了假设的地方，避免后人重踩：

1. **容灾看门狗的采样不能挂在播放进度回调上**
   `onTimeChanged` 在卡死时**恰好停止回调** —— 也就是看门狗唯一要抓的场景下它自己会停摆。改为看门狗自持时钟（1s 自调度）后，真机上才抓到卡死。

2. **「播完」会被误判成「卡死」**
   短片播到结尾时进度不再前进，窗口分数从 92 掉到 49（低于 45 阈值附近），差点把「用户正常看完」升级成换源。改为：`STATE_ENDED` **且位置到达时长（±3s）** 才算真播完、不参与评分。

3. **冻结 + 缓冲为空 时原先只扣到 49 分**（刚好高于 45 阈值）
   → 看门狗对「彻底死掉的线路」反而拒绝救援。改为冻结且饥饿时重罚（-60），实机分数从 49 降到 0.0。

4. **`(cid, key)` 索引刻意不加**
   `key` 是 PRIMARY KEY，SQLite 已有唯一 autoindex；`EXPLAIN QUERY PLAN` 显示 `find(cid,key)` / `delete(cid,key)` 在任何情况下都走 `sqlite_autoindex_History_1`，第二个索引**永远不会被选中**，只会增加写开销和体积。

5. **首帧判定用 `OnPreDrawListener` 而不是固定 `postDelayed`**
   固定延时在慢设备上会早于首帧（白做），在快设备上又白白多等。`onPreDraw` 才是「这一帧马上要画了」的真实信号。

6. **未知启动步骤默认「不许挡首屏」**
   分类表若默认放行，会随新增步骤**渐进变慢**；默认拒绝才会逼人显式表态（单测会失败提醒）。

7. **同一版本号下绝不能出现两种 schema**
   开发期间曾因设备残留「版本号 38 + 不同 schema」的中间包导致启动崩溃（`Room cannot verify the data integrity`）。这是**开发过程污染、不是产品缺陷**，但教训是：改 schema 必须同步改版本号。
